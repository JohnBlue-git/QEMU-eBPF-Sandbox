§1 Overview

For setup, kernel version, and troubleshooting, see the top-level README. This document covers the full source tree — the four canonical eBPF kernel programs, the three user-space designs built on top of them, and the QEMU guest that runs all of it.

This repository answers one question three times: given the same four eBPF kernel programs, how should user space consume the events they produce? The kernel-side logic never changes — eBPF_basic_design/<program>/<program>.bpf.c is the single canonical copy of each hook, and it is the same compiled object whether it is loaded by the procedural C loader, the OOP C++ loader, or the Boost.Asio loader. What changes across the three designs is entirely the layer that receives a ring-buffer record and turns it into a log line.

  • Basic Design (eBPF_basic_design/) — a synchronous C loader with a background pthread writer. No inheritance, no coroutines: one struct logutil_async_writer per program, guarded by a mutex and a condition variable.
  • OOP Design (eBPF_oop_design/) — a C++ loader built around one abstract base class (BpfProgram) and one action-dispatch singleton (ActionLoop) driven by hand-written C++20 coroutines.
  • Boost.Asio Design (eBPF_boost_asio_design/) — the same BpfProgram hierarchy, reused unmodified, with only the action-dispatch layer replaced by boost::asio::io_context and awaitable coroutines.
That last point is the one this whole document keeps returning to: the Boost.Asio design is not a rewrite of the OOP design — it is the OOP design's kernel-facing half left alone, and its async-facing half swapped out. See §6 for the literal proof.

§2 Build System

Three build systems, one kernel source of truth

eBPF_basic_design/Makefile is a plain Make build: it generates vmlinux.h from /sys/kernel/btf/vmlinux with bpftool, compiles each .bpf.c with clang -target bpf, and links each loader against -lbpf -lelf -lz -pthread. Neither C++ design keeps its own copy of this step. eBPF_oop_design/CMakeLists.txt and eBPF_boost_asio_design/CMakeLists.txt both regenerate their own vmlinux.h (the same bpftool btf dump command, run again in their own build directory) and then compile ../eBPF_basic_design/<example>/<example>.bpf.c directly as a custom command — there is no second source file to drift from the first, only a second compiled artifact.

Makefile
build: kernel ebpf_basic ebpf_oop ebpf_boost_asio rootfs

ebpf_basic:
	$(MAKE) -C eBPF_basic_design all

ebpf_oop:
	cmake -S eBPF_oop_design -B eBPF_oop_design/build
	cmake --build eBPF_oop_design/build

ebpf_boost_asio:
	cmake -S eBPF_boost_asio_design -B eBPF_boost_asio_design/build
	cmake --build eBPF_boost_asio_design/build

make build produces, per design, an install tree under /opt/ebpf_<design>/ — <program>.bpf.o, <program>_loader, and (Boost.Asio only) an action_runner used purely to force ActionLoop::getInstance() to start its thread at boot, independent of any loader.

Why the Boost.Asio CMakeLists.txt reaches into two other directories

eBPF_boost_asio_design/CMakeLists.txt
set(EOPPD_EBPF_SOURCE_DIR "${CMAKE_SOURCE_DIR}/../eBPF_oop_design")
set(EBPF_BASIC_SOURCE_DIR "${CMAKE_SOURCE_DIR}/../eBPF_basic_design")
...
add_executable(${example}_loader
    ${EOPPD_EBPF_SOURCE_DIR}/ebpf/BpfProgram.cpp
    ${EOPPD_EBPF_SOURCE_DIR}/${example}/${example}.cpp
    ${EOPPD_SOURCE_DIR}/${example}/main.cpp
    ${EOPPD_SOURCE_DIR}/actions/ActionLoop.cpp
    ${EOPPD_SOURCE_DIR}/actions/LogAction.cpp
)

Only two of the five source files listed there belong to eBPF_boost_asio_design/ itself (main.cpp, and its own ActionLoop.cpp / LogAction.cpp). BpfProgram.cpp and <example>.cpp are pulled from eBPF_oop_design/ verbatim — this build target does not declare a XdpDropProgram of its own, it links against the OOP design's. This is not a build-system shortcut so much as the whole point of the design: see §6.

§3 Kernel Layer: eBPF_basic_design/

Four programs, each attached to a different Linux hook, each emitting fixed-size event records through a BPF_MAP_TYPE_RINGBUF map named events:

ProgramHookIn-kernel verdictRing buffer event
xdp_drop SEC("xdp") on an interface None — always XDP_PASS {ts_ns, pkt_len, ifindex, action}
syscall_trace SEC("tracepoint/syscalls/sys_exit_{openat,read,write}") None — pure counter per-syscall event via BPF_CORE_READ(args, id)
socket_filter SEC("socket") on a raw socket Allow TCP, drop non-TCP {action=allow|drop, src, dst, protocol}
cgroup_egress SEC("cgroup_skb/egress") Deny ICMP, allow everything else {action=allow|deny, src, dst, protocol}

None of the four make a real security decision — xdp_drop's name is aspirational; it counts and observes, it does not drop. That is deliberate: this repository is a teaching sandbox for the plumbing (CO-RE, ring buffers, async user-space consumption), not a policy engine. Contrast this with HTTPS-Guard, which reuses the same primitives to actually enforce policy.

vmlinux.h is regenerated, never hand-edited: bpftool btf dump file /sys/kernel/btf/vmlinux format c > vmlinux.h. Where a field's layout could vary between kernel builds (a nested kernel struct reached through a pointer chain), the code should use BPF_CORE_READ() so libbpf can relocate the offset from the target kernel's BTF; where the field is part of the hook's own context ABI (ctx->data_end on struct xdp_md, skb->len on struct __sk_buff), direct access is correct and is what all four programs actually use. The one exception is syscall_trace.bpf.c, which reads args->id off struct trace_event_raw_sys_exit — a real kernel tracepoint struct, not a hook-context struct — through BPF_CORE_READ(args, id).

§4 Basic Design: Procedural C

eBPF_basic_design/<program>/<program>.c is a small, synchronous loader: open the .bpf.o, bpf_object__load(), attach (bpf_xdp_attach(), bpf_link__create(), or the cgroup/socket equivalent), then loop on ring_buffer__poll(). There is no class hierarchy here to diagram — the four loaders share no code beyond logging/log_utils.c, a pthread-based async writer:

logging/log_utils.h — struct shape
struct logutil_async_writer
    ├── fp, thread, lock (mutex), cond (condvar)
    ├── queue[1024][256]   — fixed-size ring of pre-formatted lines
    └── head / tail / count / dropped

logutil_writer_enqueue(line)  → producer: copies into the ring, signals cond, never blocks on I/O
writer thread                 → consumer: wakes on cond, drains queue, fwrite() + fflush()

This is the same shape the OOP and Boost.Asio designs later generalize into ActionLoop: a bounded queue, one producer (the ring-buffer poll loop), one consumer thread doing the blocking I/O, so a slow disk write never stalls ring_buffer__poll() and risks dropping kernel events.

§5 OOP Design: BpfProgram and ActionLoop

BpfProgram — one base class, four independent siblings

This is the diagram an earlier version of this document got wrong: it drew BpfProgram → XdpDropProgram → SocketFilterProgram → SyscallTraceProgram as a left-to-right chain, which reads as if one hook calls the next. They don't. All four are independent leaves inheriting from one abstract base — the correct picture is a tree, not a pipeline:

  • BpfProgram abstract · attachProgram() / detachProgram() /
    getRingBufferHandler() = 0
    • XdpDropProgram ifindex_, attached_
    • SocketFilterProgram ifindex_, sock_fd_
    • SyscallTraceProgram 3× bpf_program*,
      3× bpf_link*
    • CgroupEgressProgram cgroup_fd_, link_

loadFilter() is the one non-virtual method that sequences everything: openObject() → bpf_object__load() → attachProgram() (deferred to the subclass) → registerEventHandler(), which calls ring_buffer__new(map_fd, getRingBufferHandler(), this, nullptr). Because getRingBufferHandler() returns a static member function pointer with this passed as the ring buffer's opaque context, each subclass's callback recovers its own instance with a single static_cast<XdpDropProgram*>(ctx) — there is exactly one indirection between "a ring buffer fired" and "the right subclass instance handles it," and it is resolved once, at registerEventHandler() time, not per-event.

A hook's ringBufferHandler() is deliberately thin:

xdp_drop.cpp
int XdpDropProgram::ringBufferHandler(void *ctx, void *data, size_t data_sz) {
    ...
    auto action = std::make_unique<LogAction>(std::string(line), self->log_path_);
    ActionLoop::getInstance().pushAction(std::move(action));
    return 0;
}

Nothing about BpfProgram or its subclasses names LogAction or ActionLoop in its interface — the coupling is confined to each hook's own ringBufferHandler() body, which is free to push a different IAction or none at all.

pushAction() locks, queue_.push()s, and notifies — the caller (the ring-buffer poll thread) never blocks on I/O. pump() is the single consumer: it waits on the condvar, pops one action, and calls action->execute_async() directly on the background thread. Because execute_async() returns FireForget — a coroutine type whose initial_suspend() is suspend_never — the call starts running immediately, and the coroutine frame (not the unique_ptr<IAction> itself) is what actually outlives pump()'s scope while a file lock is pending.

That file lock is the one place this design suspends for real. AsyncFileMutex is a coroutine-aware mutex keyed by filename: co_await lock(path) either grabs the lock immediately (await_ready() == true, no suspension) or, if another LogAction already holds it, parks the coroutine handle in a per-file waiter queue and returns control to pump() — which is then free to dequeue and start the next action while the first one is still waiting on disk. unlock() pops the next waiter, if any, and resumes it directly. Task<T> (in task.hpp) is the more general awaitable of the two coroutine types in coroutine/, with a real promise_type, symmetric-transfer final_awaiter, and continuation-chaining; LogAction::execute_async() doesn't currently need it, since it never awaits another coroutine's result — but a future action composing several awaited steps would return Task<void> rather than FireForget.

§6 Boost.Asio Design: Same Hierarchy, New Executor

The single most important fact about this design is one a class diagram alone won't show: eBPF_boost_asio_design/ does not define a BpfProgram, an XdpDropProgram, or any of their three siblings. Its xdp_drop/main.cpp includes them from the other directory outright:

eBPF_boost_asio_design/xdp_drop/main.cpp
#include "../../eBPF_oop_design/xdp_drop/xdp_drop.hpp"

and its CMakeLists.txt compiles eBPF_oop_design/ebpf/BpfProgram.cpp and eBPF_oop_design/xdp_drop/xdp_drop.cpp into the Boost.Asio loader binary directly. The kernel-facing half of the OOP design — attach, detach, ring-buffer polling, the whole BpfProgram tree from §5 — is reused byte-for-byte. What this design actually replaces is IAction, ActionLoop, and LogAction's implementation — same three names, same responsibilities, different engine:

AsyncFileStreamManager (in eBPF_boost_asio_design/coroutine/async_mutex.hpp) generalizes AsyncFileMutex the same way Task<T> generalizes FireForget: instead of a bare per-file lock, acquire_stream() returns a move-only LockedStream RAII handle wrapping a cached boost::asio::posix::stream_descriptor, keyed in a stream_cache_ map so a second LogAction writing to the same path reuses the already-open file descriptor instead of paying open()/close() again. Releasing the lock happens in LockedStream's destructor rather than an explicit unlock() call — the OOP design's LogAction::execute_async() has to remember to call g_file_mgr.unlock(path_) itself; here that step cannot be forgotten, because it is not a step, it is a destructor.

work_guard_ is the detail that keeps this design's io_context_.run() thread alive between events: an io_context with an empty ready queue and no work guard simply returns from run(), which would silently stop the background thread the first time the action queue drained to empty. executor_work_guard is a no-op placeholder job that exists purely to prevent that.

§7 Event Processing Pipeline

For the OOP design (Boost.Asio's differs only in the two lines marked below):

Kernel: xdp_drop.bpf.c / syscall_trace.bpf.c / socket_filter.bpf.c / cgroup_egress.bpf.c
    │  bpf_ringbuf_reserve() → fill fields → bpf_ringbuf_submit()
    ▼
User space: <Program>::pollEvents() → ring_buffer__poll() (blocking, timeout_ms)
    │
    ▼
libbpf invokes <Program>::ringBufferHandler(ctx, data, data_sz)   (static trampoline, per hook)
    │
    ├─ static_cast<Derived*>(ctx)             — recover the owning instance
    ├─ format the event into one line
    └─ ActionLoop::getInstance().pushAction(make_unique<LogAction>(line, log_path_))
    │
════════════════ back to poll loop immediately — this call never blocks ═══════════════
    │
    ▼
ActionLoop::pushAction()
    │  OOP:         lock mutex_ → queue_.push() → cv_.notify_one()
    │  Boost.Asio:  asio::co_spawn(io_context_, ..., asio::detached)   ← different dispatch, same intent
    ▼
ActionLoop's own thread
    │  OOP:         pump() wakes on cv_, pops queue_, calls action->execute_async() (starts inline)
    │  Boost.Asio:  io_context_.run() resumes the spawned coroutine
    ▼
LogAction::execute_async()
    │  OOP:         co_await AsyncFileMutex::lock(path)       → ofstream append → unlock(path)
    │  Boost.Asio:  co_await AsyncFileStreamManager::acquire_stream(path) → async_write() → unlocks on scope exit
    ▼
/var/log/ebpf_<design>_design/<program>.events.log

The one property both C++ designs share, and the Basic Design's log_utils.c shares with them: the poll loop that talks to the kernel never performs the blocking I/O. Whatever happens between "an event arrived" and "a line is on disk" happens on a different thread (Basic Design: the writer pthread; OOP: pump(); Boost.Asio: io_context_.run()), so a slow or momentarily-locked log file cannot cause ring_buffer__poll() to fall behind and start silently dropping ring-buffer events under load.

§9 QEMU Guest Environment

scripts/build-kernel.sh builds Linux 6.1.94 by default (overridable via KERNEL_VERSION or a build-kernel.sh <version> argument) — an LTS release chosen for being feature-complete for BPF syscalls, BTF, CO-RE, tracepoints, XDP, and cgroup hooks without tracking mainline. scripts/build-rootfs.sh produces a minimal Alpine + BusyBox image sized by ROOTFS_SIZE (default 512M), and guest/init is the guest's PID 1: it mounts /proc, /sys, /cgroup2 (cgroup v2), /sys/fs/bpf, and tracefs, then picks the first non-loopback, non-tunnel network interface (is_usable_iface() filters out sit*, tunl*, gre*, dummy*, …) for XDP attachment and DHCP.

All three designs' artifacts are staged under /opt/ebpf_<design>/, but guest/init only auto-starts two of them: the Basic Design's startup block is wrapped in if false; then ... fi and is currently dead code, left in place as a template rather than deleted.

For the OOP and Boost.Asio designs, guest/init starts, per design: action_runner first (to start ActionLoop's background thread before any events can arrive), then syscall_trace_loader, then xdp_drop_loader on the detected interface (guarded by a shared /tmp/xdp_loader_started flag so only one design's XDP program attaches — only one XDP program can bind a given interface at a time, so whichever design's block runs first in the script wins it), then socket_filter_loader and cgroup_egress_loader. Output goes to /var/log/ebpf_<design>_design/*.log and *.events.log, matching the pipeline in §7.

make qemu-net (KVM, with a network interface attached) is the fastest path to a fully wired environment; make qemu-no-kvm is the fallback where /proc/cpuinfo shows no virtualization support.

§10 Related Work

HTTPS-Guard reuses the same underlying primitives this repository teaches — a kernel-side hook (uprobe/XDP/LSM), a ring buffer, and an async user-space consumer — but takes the observation one step further into an actual Detect → Classify → Dispatch pipeline: a parsed event is run through a synchronous rule (IDetection::inspect()) that returns a Verdict, and an actionable verdict is handed to boost::asio-driven enforcement actions (SOCK_DESTROY a connection, write a kernel blocklist entry).

None of the four programs in this repository classify or enforce anything — xdp_drop always returns XDP_PASS, and even socket_filter's "drop non-TCP" and cgroup_egress's "deny ICMP" are fixed, hard-coded rules rather than a pluggable rule engine. Reading this repository's BpfProgram → ActionLoop → LogAction chain is a reasonable on-ramp before reading HTTPS-Guard's programs/ → detections/ → actions/ split, since the latter is this repository's shape with a classification layer inserted between "observed" and "logged."
